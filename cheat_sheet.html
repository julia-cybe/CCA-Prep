M1 Tool Use & Agentic Loop Domain 1
Message Flow Rule
After a tool call, you MUST append both: the assistant's tool_use block + the tool_result as a user message — or the request fails.
messages = [
  {"role": "user",      "content": "What is 347 * 82?"},
  {"role": "assistant", "content": [ToolUseBlock(...)]},  ← assistant
  {"role": "user",      "content": [{"type": "tool_result",
                                     "tool_use_id": "abc",
                                     "content": "28454"}]}  ← user
]
stop_reason values
end_turn normal finish   tool_use tool needed   max_tokens surface error, don't silently loop   stop_sequence custom delimiter hit
Statefulness
In-session: stateful via the messages list. Cross-session: stateless — persist to a DB to survive restarts.
Tool selection mechanism
Tool descriptions are the primary routing mechanism. Claude matches the user request semantically to the description.
M2 Tool Choice & Parallel Calls Domain 1
tool_choiceBehavior
"auto"Default — Claude decides
"any"Force a tool call (any tool)
"none"Prohibit all tool calls
"tool" + nameForce a specific tool
Tool order matters
With "any" forced on a non-tool question, Claude picks the first tool in the list. Order your tools deliberately.
Parallel tool calls = 1 API round-trip
3 parallel tools → 1 API call (not 3). Massive latency win. Every tool_use block must have a matching tool_result in the next message — even if it's an error.
tool_results.append({
  "type": "tool_result",
  "tool_use_id": block.id,
  "content": result_or_error  # NEVER skip
})
When to use "none"
No validated/safe tools available, or for sensitive data operations where you want to prevent data sharing with external tools.
M3 Multi-Agent Systems Domain 1
Hub-and-Spoke Architecture
Subagents do NOT automatically inherit coordinator context. Every piece of info a subagent needs must be explicitly passed. Subagents never talk to each other directly.
Coordinator responsibilities
Receive goal · Decompose tasks · Inject context per subagent · Spawn (serial or parallel) · Aggregate results · Handle errors · Return final answer
Error handling pattern
Anti-patterns
Silent suppression hide failure, return partial as complete    Hard termination abort all work if one subagent fails
Correct: Graceful degradation
Classify: transient → retry with backoff · permanent → skip + report. Return successful results + clear failure attribution.
Parallel Tool Calls
  • 1 Claude instance
  • 1 API round-trip
  • Best for simple, stateless tasks
Subagents
  • Multiple instances
  • Multi-turn reasoning per agent
  • Fault isolation

M6 Tool Descriptions Domain 4
4 required elements in every tool description
1. What is the purpose of the tool
2. When to use it
3. Required input formats
4. When NOT to use it (most important for routing)
≥ 10 tools → reliability degrades
Likely due to attention dilution. Split into focused toolsets if approaching this limit.
Don't use few-shot for routing
Few-shot teaches instances, not boundaries. Edge cases are still guessed. Fix misrouting by enhancing descriptions (especially "when NOT to use").
Don't add a separate routing classifier
Descriptions already ARE the routing logic. A separate classifier is redundant, breaks on every tool rename/add, and reduces flexibility.
M7 Tool Error Handling Domain 4
Tools must ALWAYS return structured responses
Never raise an exception. Always return a structured object — even on failure.
Error TypeRetryable?Action
transientYesRetry with exponential backoff
validationOnceFix input, retry once
businessNoEscalate to human
permissionNoEscalate, do not retry
Required fields in structured error response
error_type · message · attempts (what was tried) · partial_data (if partially succeeded) · alternatives (next steps)
Silent Suppression
  • Returns success despite failure
  • Model proceeds on bad data
  • User gets misleading result
Hard Termination
  • Aborts entire workflow on 1 error
  • Discards partial successes
  • Avoidable value loss
Empty list (no results found) = success: true with an informative message, NOT an error.

Self-review is anchored to the mental model built during implementation — it misses the same blind spots. An independent instance has no prior bias.

M12 Prompt Engineering & Few-Shot Domain 3
Good instructions are specific and categorical
Vague: "only flag high-confidence issues" — undefined, inconsistent. Better: "flag if X AND Y, skip if Z" — categorical, testable.
Few-shot examples must show reasoning
An example without reasoning is padding. Include why the answer is correct — the model learns the decision logic, not just the mapping.
Don't use few-shot for tool routing
Few-shot teaches instances, not boundaries. Edge cases are still guessed. Use tool descriptions instead.
15% false-positive on one category matters
Even if overall accuracy is 2%, a 15% rate on a specific category damages user trust for that category. Aggregate metrics hide minority-class failures.
Misleading comment criterion example
Flag if: the comment describes functionality that is not reflected in the actual code behavior.
M13 JSON / Structured Output Domain 3
Schema CAN prevent
  • Wrong type
  • Missing required field
  • Value not in enum
  • Pattern mismatch
Schema CANNOT prevent
  • Hallucinated / fabricated data
  • Misread values
  • Incorrect categorization
  • Guessed absent data
Semantic error trap: strict enums without escape hatch
If a schema requires enum: ["paid","unpaid","cancelled"] but the document is ambiguous, Claude must guess. Add an "unclear" option to get honest output.
Use tool_use for structured output with no real tool
Defining a fake tool forces Claude to respond with structured JSON even when no real logic exists behind it.
Validation-retry loop failing on same field
The schema is wrong — it likely needs an "unclear" / null escape hatch. More retries won't fix a semantic error.
M14 Batch API vs. Synchronous Domain 3
Synchronous
  • User is waiting
  • Real-time response needed (<30s)
  • Full cost
Batch API
  • 50% cost savings
  • Up to 24h processing window
  • High-volume overnight workloads
custom_id is the ONLY correlation mechanism
Batch results arrive out of order. custom_id (max 64 chars) is the join key to match results back to source documents.
No multi-turn tool calling in a single batch request
Each batch request = exactly one user turn → one assistant response. Multi-turn tool calling requires a second batch (new round-trip).
Use case examples
Sync: support ticket reply expected in 30s   Batch: 10,000 contracts overnight for legal review
M15 Context Preservation Domain 5
Progressive summarization trap
Each turn summarizes history → summaries lose numbers, dates, amounts, exact policy wording. Dangerous in support, legal, and financial contexts.
Case facts block pattern
Keep a persistent structured dict of critical facts. Inject it verbatim into every prompt — never summarize it. Only update when agent explicitly writes to the block.
"Lost in the middle" effect
Models attend reliably to the start and end of context. Middle content (e.g. pages 20–35 of a long doc) is under-attended. Fix: put critical facts at the TOP, close with a key summary, use explicit section headers.
Trim tool outputs
Raw API/DB responses pad the middle. Extract only the fields actually needed before injecting into context. Fewer tokens in the middle = less competition for attention.
M16 Escalation & Human-in-the-Loop Domain 5
Valid escalation triggers
  • Explicit request: "I want a human" → always escalate
  • Policy gap: no policy covers the case → never invent rules
  • No progress: repeated failed attempts → escalate after N retries
Invalid escalation triggers
  • Sentiment alone: frustrated + easy issue → resolve with empathy
  • Self-reported confidence: "90% confident" is unreliable on hard cases
  • Emotion keywords: "angry" ≠ escalation needed
Sentiment is a signal, NOT a trigger
Frustrated customer + straightforward, policy-covered issue → resolve with empathy. Escalating wastes human capacity.
Confidence scores are unreliable
Models report high confidence while being wrong on hard cases (adversarial inputs, edge cases, out-of-distribution data). Never use confidence scores alone as a routing trigger.
Aggregate vs. stratified accuracy
97% overall accuracy can hide 40% error rate on one document type. Always check stratified accuracy by subgroup — aggregate metrics hide minority-class failures.
M17 Error Propagation in Multi-Agent Systems Domain 5
Structured error context from failing subagent
failure_type: transient | validation | business | permission
what_was_attempted: specific operation that failed
partial_results: data successfully retrieved before failure
alternatives: suggested next steps / fallback paths
Silent Suppression
  • Coordinator hides failure, returns "success"
  • Downstream agents decide on incomplete data without knowing it
  • Impossible to debug
Hard Termination
  • One failure aborts entire workflow
  • Partial results from successful subagents discarded
  • User gets nothing when they could get partial value
Access failure vs. valid empty result
Access failure: tool/API couldn't be reached → structured error, trigger recovery
Valid empty: tool ran fine, found nothing → success=true, empty data, informative message
Confusing these wastes tokens (retrying valid empties) or hides real data loss (swallowing access failures).
Graceful degradation output
Return partial results from succeeded subagents + clearly attribute which subagent failed, why, and what was attempted + suggest alternatives.
★ Key Architecture Patterns & Exam Traps
Control flow via tool_use
Never parse natural language for control flow (if "Research complete:" in response). Define a research_complete() tool instead — gives deterministic stop_reason: tool_use.
In-context vs. external state
In-context: the messages list — valid only for the session. External: DB / files — persists across sessions. Must explicitly save to persist.
3 separate MCPs > 1 orchestrator
For Postgres + Jira + CRM: 3 separate MCP servers. Better tool discovery, availability, and isolation per system.
Attention dilution checklist
Long doc → two-pass approach
Many tools (>10) → review descriptions
Long context → critical facts at TOP
Verbose tool output → trim before inject
